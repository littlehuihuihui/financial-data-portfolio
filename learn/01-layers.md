# 第 01 章 · 数仓怎么建：五层架构与 Kimball 建模

## 1. 本章目标

1. 独立完成「主题域立项」：业务过程 → 粒度 → 维度 → 事实（Kimball 四步）。  
2. 准确表述 ODS / DIM / DWD / DWS / ADS 的职责、输入输出、典型表类型。

## 2. 先建模，后建表（Kimball 四步详解）

很多失败项目的共同特征：**还没想清楚「一行代表什么」，就开始拉宽表**。Kimball 强制你按顺序回答四个问题。

### 2.1 选择业务过程（Business Process）

业务过程 = 企业中可观测、可度量的一次「发生」。

- 好的例子：用户完成一笔订购；一次开机事件；一张质检单关闭；一笔费用入账。  
- 差的例子：「用户体验」「数字化转型」（不可直接度量）。

**原则**：一个主题域通常对应一个（或一组密切相关的）业务过程；不要把「所有 APP 行为」糊成一个过程而不拆分。

### 2.2 声明粒度（Grain）——最重要的一句

粒度 = **事实表一行到底代表什么**，必须唯一、可检验。

| 粒度声明 | 可用性 |
|----------|--------|
| 一行 = 一次 Launcher 操作事件 | 可做漏斗、路径（若有序列） |
| 一行 = 某日某设备是否活跃 | 适合日活，不适合事件细节 |
| 一行 = 某月某门店毛利 | 适合经营月报，不能回放单笔订单 |

**铁律**：DWD 与 DWS 的粒度不同时，必须分别声明；汇总会 **丢失细节**，不可逆。

### 2.3 确定维度（Dimensions）

维度 = 观察事实的角度：何时、何地、何人、何物、何渠道。

- 一致性维度（Conformed Dimensions）：跨主题共用同一 `dim_date` / `dim_device`，避免「两个日期维对不上」。  
- 退化维度：订单号等可留在事实表。  
- 雪花：维表再拆上级维（如地市→省份），查询更规范，但 Join 更深。

### 2.4 确定事实（Facts）

事实 = 可加度量（additive）或半可加/不可加度量：

- 可加：金额、次数、时长（在声明的粒度上）  
- 半可加：余额（不能跨时间乱加）  
- 不可加：比率（应在汇总后计算，或放 ADS）

## 3. 五层架构详解（每一层「存什么 / 不存什么」）

### 3.1 ODS · 操作数据层（贴源）

**目的**：把源系统数据「搬进来」，尽量少改语义，形成可重跑的原始落地层。

| 项 | 说明 |
|----|------|
| 结构 | 接近源表/日志 Schema |
| 质量 | 允许脏数据存在，但要可追踪批次 |
| 消费者 | **仅** DWD 构建与 DIM 构建过程 |
| 典型类型 | 增量日志、日全量快照、文件落地 |

互联网例子：`ods_log_launcher_di`（埋点）、`ods_order_di`（订购库）。  
零售例子：订单/支付/库存 ODS，可能来自业务库或第三方文件。  
制造例子：工单、质检、设备采集。

**ODS 设计清单**：主键/业务键、事件时间、入库时间、来源系统、批次号；注释标明增量/全量/快照。

### 3.2 DIM · 维度层

**目的**：企业级一致性描述信息，供事实关联。

- 代理键（surrogate key）vs 业务键——**以项目 DDL 为准**  
- > **证据**：OTT `dim_device` 以业务键 `mac` 为 PRIMARY KEY（`ott_ddl.sql`），**不是** surrogate `device_sk`，也**不是** SCD2 拉链（详见 E1）  
- 变化策略：覆盖更新 / 快照 / 拉链——必须能在 COMMENT 或专题中指认  
- 未知维：OTT 多处默认 `'-1'` 字符串（见 `dim_device.model_id` 等 DEFAULT）

### 3.3 DWD · 明细数据层

**目的**：在 **声明粒度** 上的干净事实：清洗、标准化码值、补维键、统一时区/币种。

- 命名常 `dwd_*` 或 `fact_*`  
- 一行对应业务过程的一次发生（或明确的明细快照）  
- **禁止**在 DWD 里堆「所有看板指标」；指标下沉到 DWS/ADS

互联网：`dwd_act_launcher_di`、`dwd_vod_play_di`、`dwd_trade_order_di`。

### 3.4 DWS · 汇总数据层

**目的**：按分析高频粒度预聚合，形成可复用的公共指标集。

- 典型粒度：日×用户、日×内容、月×门店、日×产线  
- 字段多为可加度量 + 维度外键  
- 多个 ADS / 多个看板应优先复用同一 DWS，避免各算各的

互联网：`dws_act_user_active_1d`、`dws_trade_order_1d`。

### 3.5 ADS · 应用数据层

**目的**：面向具体应用（某张看板、某类角色）的指标切片；常为视图或轻量表。

- 可做比率、排名、同比、口径拼装  
- **应读取 DWS（或必要时 DWD，需说明例外）**，不直连 ODS  
- 「实时」常常是：视图查询时计算，而依赖的 DWS 仍是 T+1 批次

互联网：`v_dau_overview`、`v_funnel`、`v_retention_decomposition`。

## 4. 层次调用规范（必须会背）

```
源系统 ──采集──▶ ODS ──清洗+关联DIM──▶ DWD ──聚合──▶ DWS ──封装──▶ ADS ──▶ 看板
                      ▲
                     DIM
```

强制纪律（与本仓库规范一致）：

1. ODS 只被 DWD（及 DIM 构建）引用。  
2. 禁止 ADS / DWS 直接查 ODS。  
3. 新看板 / 方法论 SQL 落在 DWS 或 ADS。  
4. 反向依赖（除明确回写）禁止。

**为什么禁止 ADS 读 ODS？**  
因为 ADS 会把源波动、脏数据、未清洗码值直接暴露给业务；且无法复用汇总，每次全扫日志。

## 5. 字段与表类型规范（实用）

| 类型 | 规范 |
|------|------|
| 金额 | `DECIMAL(15,2)` + 单位注释 |
| ID | 优先 `BIGINT`；业务字符串 ID 在注释说明 |
| 日期 | `DATE` 或 `YYYY-MM-DD` 字符串 |
| 维 NULL | `-1` |
| 指标 NULL | `0` |

表类型：增量 / 全量 / 快照 / 拉链——建表 COMMENT 必须写清。  
字段数下限：ODS≥10、DWD 事实≥15、维≥10、DWS≥8、ADS 输出≥5（不足则补业务可解释字段，禁止注水）。

## 6. 作品集实例（互联网主线）

主题域示例：**开机活跃**

1. 业务过程：用户/设备产生 Launcher 行为  
2. 粒度：DWD=行为明细；DWS=日活跃汇总  
3. 维度：日期、设备、产品线等  
4. 事实：活跃次数、时长、是否有效等  

落表：`ods_log_launcher_di` → `dwd_act_launcher_di` → `dws_act_user_active_1d` → `v_dau_overview`。

### 三行业对照

| | 互联网 | 零售 | 制造 |
|--|--------|------|------|
| 过程 | 行为/订购 | 成交/入出库/费用 | 工单/质检/设备运行 |
| DWS 时钟 | 多为日 | 日+月财务 | 日产质量+月成本 |
| ADS | 活跃/漏斗/留存 | 利润表/杜邦/现金流 | 产量/OEE/良率 |
