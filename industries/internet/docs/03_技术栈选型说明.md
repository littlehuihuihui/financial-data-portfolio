# 技术栈选型与数据源接入规范（互联网行业）

## 一、技术栈选型说明

### 1.1 选型原则
- **本地开发优先**：个人学习/作品集使用MySQL，轻量易部署，SQL标准兼容
- **生产环境分层**：根据数据规模和实时性要求选择不同技术栈，避免过度设计
- **云原生优先**：优先选择阿里云生态，符合DataWorks规范
- **平滑迁移**：本地SQL 90%以上兼容生产环境Hive语法，迁移成本低

### 1.2 各环境技术栈对比

| 组件 | 本地开发环境 | 中小企业生产 | 中大型企业生产 | 集团级（阿里云） |
|------|-------------|-------------|---------------|----------------|
| **关系型数据库** | MySQL 8.0 | MySQL 8.0 | MySQL/PostgreSQL | PolarDB |
| **数仓存储（离线）** | MySQL 8.0 | Hive 3.x (HDFS) | Hive 3.x (HDFS) | MaxCompute(ODPS) |
| **OLAP查询引擎** | MySQL视图 | ClickHouse 23.x | ClickHouse + Presto/Trino | Hologres + ClickHouse |
| **实时计算** | - | Flink 1.17 | Flink 1.17 + Kafka | Realtime Compute + Kafka |
| **埋点采集** | 手动造数据 | SDK + LogAgent | SDK + Flume/LogAgent | 数据总线DataHub |
| **数据集成** | 存储过程 | DataX + Canal | DataX + Flink CDC | DataWorks数据集成 |
| **任务调度** | 手动/crontab | DolphinScheduler 3.x | Airflow/DolphinScheduler | DataWorks调度 |
| **用户标签/画像** | - | MySQL + Redis | ClickHouse + HBase | Hologres + HBase |
| **消息队列** | - | Kafka | Kafka | Kafka |
| **数据质量** | - | 自定义SQL监控 | Apache Griffin | DataWorks数据质量 |
| **元数据管理** | 文档 | Datahub | Datahub/Atlas | DataWorks数据地图 |
| **可视化** | ECharts HTML | Metabase/Grafana | Tableau/Power BI | Quick BI + DataV |

### 1.3 为什么互联网行业选ClickHouse？
1. **写入性能强**：每秒百万级写入，适合海量埋点数据实时写入
2. **查询速度快**：单表亿级数据秒级响应，适合用户行为多维分析
3. **列式存储**：宽表场景性能极佳，适合用户画像、标签分析
4. **实时性好**：支持实时写入实时查询，分钟级数据延迟
5. **运维简单**：单机也能跑，集群扩展方便，适合中小团队

### 1.4 为什么本地用MySQL？
1. **轻量易部署**：一个Docker即可启动，不需要Hadoop集群
2. **SQL标准兼容**：DDL/DML语法和Hive/ClickHouse高度兼容
3. **学习成本低**：大多数分析师都熟悉MySQL语法
4. **性能足够**：百万级用户行为数据MySQL完全能支撑学习和演示
5. **作品集友好**：面试官不需要搭环境就能跑起来看效果

## 二、数据源接入规范

### 2.1 互联网源系统清单

| 源系统 | 系统类型 | 数据库/格式 | 核心数据 | 接入方式 | 同步频率 | 负责人 |
|-------|---------|------------|---------|---------|---------|--------|
| **业务库（用户/订单）** | 业务系统 | MySQL | 用户信息、订单、支付、会员 | DataX离线 + Canal实时 | T+1 + 准实时 | 后端组 |
| **埋点SDK** | 行为采集 | 日志/JSON | 页面浏览、点击、事件、曝光 | SDK→LogAgent→Kafka→Flink | 实时（分钟级） | 数据组 |
| **广告投放平台** | 第三方 | API接口 | 渠道消耗、点击、展示、转化 | API拉取 | T+1 凌晨 | 投放组 |
| **CRM系统** | 用户运营 | MySQL | 用户标签、触达记录、活动 | DataX离线同步 | T+1 凌晨 | 运营组 |
| **服务端日志** | 技术日志 | 日志文件 | 接口请求、错误日志、性能指标 | Filebeat→Kafka→ES | 实时 | 运维组 |
| **第三方数据** | 外部数据 | Excel/API | 设备画像、地理位置、风控数据 | 手动/API导入 | 不定期 | 数据组 |

### 2.2 数据同步策略

#### 离线同步（T+1）
```
适用场景：用户基础信息、订单、财务、渠道数据等非实时数据
调度时间：每日凌晨2:00-6:00业务低峰期
同步方式：DataX全量+增量结合
- 小表（<100万）：每日全量覆盖
- 大表（>100万）：基于updated_at增量同步
- 历史分区：按dt天分区，保留180天明细
```

#### 准实时同步（CDC）
```
适用场景：订单状态、用户注册、支付等需要分钟级更新的数据
同步方式：Canal/Debezium捕获binlog → Kafka → Flink清洗 → 写入DWD
延迟要求：<5分钟
```

#### 实时埋点流（分钟级）
```
适用场景：用户行为埋点、实时看板、实时活动效果监控
同步方式：Web/App SDK上报 → Nginx/网关 → Kafka → Flink实时ETL → ClickHouse
延迟要求：<3分钟
```

### 2.3 ODS层数据映射规则

| 源表/日志 | ODS目标表 | 字段映射规则 | 清洗规则 |
|----------|----------|-------------|---------|
| user库.users | ods_user_info | 字段名统一下划线命名 | 空值替换、脱敏、去重 |
| order库.orders | ods_order_info | 订单号统一格式 | 状态码映射、时间格式统一 |
| 埋点event日志 | ods_user_event | event_id/user_id/属性JSON解析 | 异常事件过滤、空用户过滤 |
| 广告平台API | ods_channel_cost | 渠道编码统一 | 金额校验、时间对齐 |
| 支付库.payment | ods_payment | 支付流水号统一 | 状态映射、重复支付过滤 |
| CRM用户标签 | ods_user_tag | 用户ID统一 | 标签编码标准化 |

## 三、各层ETL处理规范

### 3.1 ODS层 ETL规范
```sql
-- ODS层标准处理模板（埋点数据）
INSERT OVERWRITE TABLE ods.ods_user_event PARTITION(dt='${dt}')
SELECT
    user_id,
    event_id,
    event_time,
    page_id,
    -- JSON属性解析
    get_json_object(properties, '$.source') AS source,
    get_json_object(properties, '$.duration') AS duration,
    device_id,
    ip,
    -- 审计字段
    CURRENT_TIMESTAMP() AS etl_time,
    '${dt}' AS dt
FROM source.user_event_log
WHERE dt = '${dt}'
  AND user_id IS NOT NULL -- 过滤未登录用户（根据业务需要）
  AND event_time BETWEEN '${dt} 00:00:00' AND '${dt} 23:59:59'
  -- 去重：同一用户同一事件同一毫秒只保留一条
  QUALIFY ROW_NUMBER() OVER(PARTITION BY user_id, event_id, event_time ORDER BY etl_time DESC) = 1;
```

**ODS层必须做的清洗：**
1. 字段类型统一（字符串转数字、时间格式转换）
2. 空值处理（NULL替换为默认值/UNKNOWN/-1）
3. 敏感数据脱敏（手机号、身份证、姓名）
4. 主键/事件去重
5. 增加dt分区字段和etl_time时间戳
6. 异常数据过滤（测试数据、爬虫数据）

### 3.2 DIM层 ETL规范
```sql
-- 维度拉链表SCD2处理模板（用户维度）
INSERT INTO dim.dim_user
SELECT
    user_id,
    user_name,
    gender,
    age,
    city,
    level,
    register_time,
    start_date,
    CASE WHEN end_date = '9999-12-31' AND old.user_id IS NOT NULL THEN DATE_SUB('${dt}', INTERVAL 1 DAY)
         ELSE end_date END AS end_date,
    is_current
FROM dim.dim_user
UNION ALL
-- 新增/变更的数据
SELECT
    user_id,
    user_name,
    gender,
    age,
    city,
    level,
    register_time,
    '${dt}' AS start_date,
    '9999-12-31' AS end_date,
    1 AS is_current
FROM ods.ods_user_info
WHERE dt = '${dt}';
```

**DIM层必须做的处理：**
1. 维度一致性：所有维度表在DIM层统一，各业务线共用
2. 缓慢变化维：用户等级、会员等重要属性用SCD2拉链表保留历史
3. 维度退化：常用编码字段退化到事实表
4. 未知维度：关联不上的维度用-1表示，不允许NULL外键
5. 用户脱敏：敏感字段统一脱敏处理

### 3.3 DWD层 ETL规范
```sql
-- DWD层事实表模板（用户行为事实表）
INSERT OVERWRITE TABLE dwd.dwd_user_event_fact PARTITION(dt='${dt}')
SELECT
    e.user_id,
    d.date_id,
    u.user_level,
    u.city,
    e.event_id,
    e.page_id,
    e.source,
    e.duration,
    e.device_id,
    -- 衍生指标
    CASE WHEN e.event_id = 'page_view' THEN 1 ELSE 0 END AS is_pv,
    CASE WHEN e.event_id = 'click' THEN 1 ELSE 0 END AS is_click,
    -- 会话标识（30分钟切分）
    SUM(CASE WHEN TIMESTAMPDIFF(SECOND, last_event_time, e.event_time) > 1800 THEN 1 ELSE 0 END)
        OVER(PARTITION BY e.user_id ORDER BY e.event_time) AS session_id,
    CURRENT_TIMESTAMP() AS etl_time
FROM ods.ods_user_event e
LEFT JOIN dim.dim_date d ON DATE(e.event_time) = d.date
LEFT JOIN dim.dim_user u ON e.user_id = u.user_id AND u.is_current = 1
WHERE e.dt = '${dt}'
  AND e.user_id != '-1';
```

**DWD层必须做的处理：**
1. 粒度统一：同一张事实表必须是同一粒度（事件粒度/会话粒度/天粒度）
2. 维度关联：关联所有维度表，维度外键不允许NULL
3. 事件清洗：过滤测试事件、异常事件、爬虫数据
4. 会话切分：用户行为数据按30分钟无操作切分会话
5. 衍生字段：基础衍生指标在DWD层计算好

### 3.4 DWS层 ETL规范
```sql
-- DWS层汇总表模板（用户日汇总表）
INSERT OVERWRITE TABLE dws.dws_user_daily PARTITION(dt='${dt}')
SELECT
    date_id,
    user_id,
    user_level,
    city,
    COUNT(DISTINCT session_id) AS session_count,
    SUM(is_pv) AS pv_count,
    SUM(is_click) AS click_count,
    SUM(duration) AS total_duration,
    COUNT(DISTINCT page_id) AS page_count,
    -- 首次/末次访问时间
    MIN(event_time) AS first_visit_time,
    MAX(event_time) AS last_visit_time,
    CURRENT_TIMESTAMP() AS etl_time
FROM dwd.dwd_user_event_fact
WHERE dt = '${dt}'
GROUP BY date_id, user_id, user_level, city;
```

**DWS层必须做的处理：**
1. 公共粒度：按通用维度组合聚合（用户天/渠道天/页面天）
2. 指标复用：所有公共指标在DWS层统一计算，ADS层直接引用
3. 层级聚合：日→周→月→季→年逐层聚合，复用下层数据
4. 主题划分：按用户/行为/渠道/营收主题域划分

### 3.5 ADS层 ETL规范
```sql
-- ADS层视图模板（DAU看板）
CREATE VIEW ads.ads_dau_dashboard AS
SELECT
    stat_date,
    COUNT(DISTINCT user_id) AS dau,
    COUNT(DISTINCT CASE WHEN is_new_user = 1 THEN user_id END) AS new_user_count,
    SUM(pv_count) AS total_pv,
    AVG(total_duration) AS avg_duration,
    AVG(session_count) AS avg_session_count
FROM dws.dws_user_daily
GROUP BY stat_date;
```

**ADS层必须遵守的规则：**
1. 只从DWS取数，禁止直接从DWD/DIM关联
2. 优先用视图，保证数据一致性
3. 一个报表/看板对应一个ADS视图
4. 字段名直接和报表字段对应，不做二次计算

## 四、SQL兼容性说明（MySQL → Hive/ClickHouse）

本地MySQL SQL迁移到生产环境只需要修改以下几点：

| MySQL语法 | Hive语法 | ClickHouse语法 | 说明 |
|----------|---------|---------------|------|
| AUTO_INCREMENT | row_number()生成 | 不用自增，用UUID/雪花ID | 主键生成方式 |
| DATE_FORMAT() | date_format() | formatDateTime() | 时间格式化 |
| IFNULL() | nvl() / coalesce() | ifNull() / coalesce() | 空值处理 |
| NOW() | current_timestamp() | now() | 当前时间 |
| STR_TO_DATE() | to_date() | toDate() / toDateTime() | 时间转换 |
| GROUP_CONCAT() | collect_list/collect_set | groupArray / groupUniqArray | 字符串聚合 |
| JSON_EXTRACT() | get_json_object() | JSONExtractString/Int | JSON解析 |
| INSERT OVERWRITE | INSERT OVERWRITE + 分区 | INSERT + OPTIMIZE | 覆盖写入 |
| 窗口函数 | 支持 | 支持 | 基本一致 |

> 整体兼容性90%以上，核心业务逻辑不需要修改，只需要调整少量函数语法。
