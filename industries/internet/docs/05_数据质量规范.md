# 互联网行业 · 数据质量规范 v3.1

> 埋点数据、实时数据、A/B测试全链路质量保障，保证分析结论可靠

---

## 一、数据质量6维度体系

### 1.1 完整性（Completeness）

| 监控对象 | 监控规则 | 阈值要求 | 告警级别 | 处理方式 |
|---------|---------|---------|---------|---------|
| 埋点事件 | 事件上报量与历史基线对比，波动超过阈值告警 | 波动 ±20% | P1 高 | 排查埋点上报、SDK版本、网络问题 |
| 用户维度 | user_id非空率 | > 99.5% | P1 高 | 排查未登录用户、SDK异常 |
| 事件属性 | 核心事件必填属性非空率 | > 99% | P2 中 | 排查埋点代码、属性上报逻辑 |
| 订单数据 | 订单条数与业务库对比 | 差异率 < 0.01% | P1 高 | 补数，确保交易数据完整 |
| 实时数据 | 实时延迟数据量与离线T+1对比 | 差异率 < 2% | P2 中 | 排查实时链路丢数据 |

### 1.2 准确性（Accuracy）

| 监控对象 | 监控规则 | 阈值要求 | 告警级别 | 处理方式 |
|---------|---------|---------|---------|---------|
| 事件去重 | 同一用户同一事件同一毫秒重复上报 | 重复率 < 0.1% | P2 中 | 去重逻辑优化，SDK防抖 |
| 数值合理性 | 时长、金额等数值在合理范围内 | 异常率 < 0.5% | P2 中 | 异常值过滤，标记异常 |
| 枚举值合法 | 事件类型、状态等枚举值在字典内 | 异常率 = 0% | P2 中 | 统一枚举，脏数据过滤 |
| 金额准确性 | 订单金额与业务库对账 | 差异率 = 0% | P0 紧急 | 逐笔核对，补数修正 |
| 用户身份 | user_id与用户表匹配率 | > 99% | P1 高 | 排查异常用户、测试账号 |

### 1.3 一致性（Consistency）

| 监控对象 | 监控规则 | 阈值要求 | 告警级别 | 处理方式 |
|---------|---------|---------|---------|---------|
| 实时离线一致性 | 实时看板DAU与离线T+1 DAU对比 | 差异率 < 2% | P2 中 | 排查实时计算逻辑、延迟数据 |
| 跨表一致性 | 订单表和支付表金额一致 | 差异率 < 0.01% | P1 高 | 逐笔核对，找出差异单据 |
| 指标口径一致性 | 同一指标在不同看板数值一致 | 差异 = 0 | P1 高 | 统一口径，修正错误计算逻辑 |
| 维度一致性 | 渠道、版本等维度编码统一 | 匹配率 = 100% | P2 中 | 统一维度字典，映射转换 |
| 时区一致性 | 所有时间统一北京时间（UTC+8） | 异常率 = 0% | P2 中 | 上报时统一时区转换 |

### 1.4 及时性（Timeliness）

| 数据类型 | 产出延迟要求 | 告警阈值 | 业务影响 |
|---------|-----------|---------|---------|
| 实时埋点数据 | 从上报到可查询 < 3分钟 | 延迟 > 5分钟告警 | 实时看板不准，活动监控延迟 |
| 实时订单数据 | 从支付到可查询 < 1分钟 | 延迟 > 3分钟告警 | 营收监控延迟，异常发现慢 |
| 离线ODS层 | 每日凌晨6:00前完成 | 延迟 > 30分钟告警 | 影响后续ETL |
| 离线DWD/DWS层 | 每日凌晨8:00前完成 | 延迟 > 30分钟告警 | 影响早会看板 |
| ADS看板数据 | 每日上午9:00前可用 | 延迟 > 1小时告警 | 日报延迟 |

### 1.5 有效性（Validity）

| 监控对象 | 监控规则 | 阈值要求 | 告警级别 |
|---------|---------|---------|---------|
| 时间格式 | 事件时间格式合法，在合理范围（未来/太久远） | 异常率 < 0.1% | P2 中 |
| IP地址 | IP格式合法，可解析地理位置 | 异常率 < 1% | P3 低 |
| 设备ID | 设备ID格式符合规范 | 异常率 < 0.5% | P3 低 |
| URL/页面路径 | 页面路径在配置范围内 | 异常率 < 2% | P3 低 |
| 敏感数据 | 用户手机号、身份证等已脱敏 | 脱敏率 = 100% | P1 高 |

### 1.6 唯一性（Uniqueness）

| 监控对象 | 监控规则 | 阈值要求 | 告警级别 |
|---------|---------|---------|---------|
| 事件ID | 每个事件唯一标识不重复 | 重复率 < 0.1% | P2 中 |
| 订单号 | 同一订单号唯一 | 重复率 = 0% | P0 紧急 |
| 用户ID | 用户表主键唯一 | 重复率 = 0% | P1 高 |
| 会话ID | 同一会话ID唯一 | 重复率 < 0.5% | P3 低 |

## 二、埋点数据专项质量规范

### 2.1 埋点质量保障流程

| 阶段 | 质量活动 | 责任人 | 产出 |
|------|---------|--------|------|
| **设计阶段** | 埋点需求评审、埋点文档评审、属性定义确认 | 产品+数据 | 埋点需求文档、埋点字典 |
| **开发阶段** | 埋点代码开发、自测、Code Review | 前端/后端+数据 | 埋点代码、自测报告 |
| **测试阶段** | 埋点测试、属性校验、边界场景测试 | 测试+数据 | 埋点测试报告 |
| **上线阶段** | 灰度验证、流量对比、核心指标校验 | 数据+产品 | 上线验证报告 |
| **运行阶段** | 日常监控、异常告警、定期巡检 | 数据工程师 | 质量监控看板 |

### 2.2 埋点数据清洗规则

```sql
-- DWD层埋点数据标准清洗逻辑
INSERT OVERWRITE TABLE dwd.dwd_user_event_fact PARTITION(dt='${dt}')
SELECT
    user_id,
    event_id,
    event_time,
    page_id,
    device_id,
    -- 1. 过滤测试账号
    CASE WHEN user_id IN (SELECT test_user FROM dim_test_user) THEN NULL ELSE user_id END AS user_id_clean,
    -- 2. 过滤未来时间和太久远的异常时间
    CASE WHEN event_time BETWEEN DATE_SUB('${dt}', 7) AND DATE_ADD('${dt}', 1) 
         THEN event_time ELSE NULL END AS event_time_clean,
    -- 3. 异常时长过滤
    CASE WHEN duration BETWEEN 0 AND 3600 THEN duration ELSE NULL END AS duration_clean
FROM ods.ods_user_event
WHERE dt = '${dt}'
  -- 4. 空事件过滤
  AND event_id IS NOT NULL
  AND event_id != ''
  -- 5. 爬虫/机器人过滤（简单规则，生产用更复杂的反作弊）
  AND user_id NOT IN (SELECT user_id FROM ods_blacklist)
  -- 6. 去重：同一用户同一事件同一毫秒只保留一条
  QUALIFY ROW_NUMBER() OVER(PARTITION BY user_id, event_id, event_time ORDER BY etl_time DESC) = 1;
```

### 2.3 常见埋点质量问题

| 问题类型 | 现象 | 原因 | 解决方案 |
|---------|------|------|---------|
| **埋点漏报** | 某个事件突然没有数据 | 版本发布漏埋、页面改版、SDK报错 | 埋点回归测试、监控告警 |
| **埋点多报** | 事件数异常偏高 | 重复触发、SDK重发机制、页面自动刷新 | 前端防抖、服务端去重 |
| **属性缺失** | 核心属性空值率高 | 前端没传、传错了、类型不对 | 埋点测试加强、非空校验 |
| **属性值错误** | 枚举值不对、数值异常 | 前后端联调问题、单位不统一 | 统一枚举字典、数据校验 |
| **用户身份错乱** | user_id为空、匿名用户多 | 未登录状态、登录态切换问题 | 统一用户身份体系、匿名用户映射 |

## 三、A/B测试数据质量规范

### 3.1 实验前质量校验
1. **分流均匀性检验**：实验组和对照组用户特征（历史行为、设备、地域）分布一致，卡方检验P值>0.05
2. **样本量计算**：根据基线指标、预期提升、显著性水平、统计功效计算所需样本量，避免实验不显著
3. **互斥性校验**：同一用户不会同时进入多个互斥实验
4. **埋点校验**：实验相关埋点已验证，数据上报正常

### 3.2 实验中质量监控
1. **指标异常监控**：核心指标异常波动告警
2. **分流比例监控**：实验组分流比例符合预期（如50/50）
3. **新奇效应监控**：实验前几天数据是否异常，排除用户新鲜感影响
4. **辛普森悖论防范**：分人群看效果，避免整体和分层结论相反

### 3.3 实验后质量验证
1. **统计显著性检验**：P值<0.05才认为有显著差异
2. **置信区间计算**：给出指标提升的置信区间，不只看点估计
3. **多重检验校正**：多个指标同时检验时，用Bonferroni等方法校正
4. **长期效应验证**：核心实验上线后跟踪长期效果，避免短期优化长期受损

## 四、质量问题处理流程

### 4.1 告警分级
- **P0 紧急**：核心交易数据错误、订单数据丢失、实时数据中断 → 30分钟响应
- **P1 高**：DAU等核心指标异常波动、埋点大面积漏报 → 2小时响应
- **P2 中**：非核心指标异常、少量属性缺失、延迟轻度超标 → 当日响应
- **P3 低**：格式问题、边缘场景、优化建议 → 排期处理

### 4.2 数据修复SOP
1. **影响评估**：评估影响范围、下游依赖、是否需要暂停看板
2. **根因定位**：从SDK→网关→Kafka→Flink→数仓逐层排查
3. **修复方案**：
   - 源数据问题：通知业务方修正，重新同步
   - ETL逻辑问题：修正代码，重跑历史数据
   - 埋点问题：前端修复，历史数据尽量补全或标记
4. **验证发布**：质量校验通过后，重新发布数据
5. **复盘优化**：记录问题，补充监控规则，避免再发
